## 面向 Claude Opus 4.7 的提示词

Claude Opus 4.7 是我们最强大的通用模型，在长周期智能体任务、知识工作、视觉和记忆任务方面尤其出色。它在现有 Claude Opus 4.6 的提示词上开箱即用表现良好。以下模式涵盖了最常需要调整的行为。

<Note>
有关从 Claude Opus 4.6 迁移时的 API 参数变更（effort 级别、task budget、思考配置、采样参数移除以及 tokenization），请参阅[迁移指南](/docs/en/about-claude/models/migration-guide#migrating-to-claude-opus-4-7)。
</Note>

### 回复长度与冗余度

Claude Opus 4.7 会根据自身对任务复杂度的判断来校准回复长度，而不是默认固定某种冗余度。这意味着在简单查询上通常会得到更短的答案，而在开放式分析上会得到更长的答案。

如果你的产品依赖某种特定的输出风格或冗余度，你可能需要调整提示词。例如，要减少冗余，可以添加：

```text
提供简洁、聚焦的回复。跳过非必要的背景信息，示例保持最简。
```

如果你看到了特定类型的冗余（例如过度解释），可以在提示词中添加额外指令来阻止它们。正向示例——展示 Claude 如何以恰当的简洁程度沟通——通常比告诉模型“不要做什么”的负向指令更有效。

### 校准 effort 与思考深度

[effort 参数](/docs/en/build-with-claude/effort) 允许你在智能程度与 token 消耗之间进行调优，用能力换取更快的速度和更低的成本。对于编码和智能体用例，建议从新的 `xhigh` effort 级别开始；对于大多数对智能敏感的用例，至少使用 `high` effort。可以尝试其他 effort 级别，进一步微调 token 用量与智能程度：

- **`max`**：最大 effort 在某些用例中可以带来性能提升，但可能因 token 用量增加而出现收益递减。这个设置有时也容易导致过度思考。我们建议在智能密集型任务上测试 max effort。
- **`xhigh`（新增）**：额外高 effort 是大多数编码和智能体用例的最佳设置。
- **`high`**：该设置在 token 用量与智能程度之间取得平衡。对于大多数对智能敏感的用例，我们建议至少使用 `high` effort。
- **`medium`**：适用于对成本敏感、需要在降低 token 用量的同时牺牲一定智能程度的用例。
- **`low`**：保留给短小、范围明确的任务以及对延迟敏感但对智能不敏感的工作负载。

与 Claude Opus 4.6 相比有显著变化：Claude Opus 4.7 严格遵循 effort 级别，尤其是在低级别时。在 `low` 和 `medium` 级别下，模型会将其工作范围限定在被问及的任务上，而不是额外发挥。这对延迟和成本有利，但在中等复杂度的任务上使用 `low` effort 存在思考不足的风险。

如果在复杂问题上观察到浅层推理，请将 effort 提升到 `high` 或 `xhigh`，而不是通过提示词来解决。如果因为延迟原因必须保持 `low` effort，可以添加针对性指导：

```text
此任务涉及多步推理。在回复前请仔细思考问题。
```

我们预计 effort 对该模型的重要性超过以往任何 Opus 模型，并建议在升级时积极尝试该参数。

自适应思考的触发行为是可引导的。如果发现模型思考的频率过高（这可能在大型或复杂的系统提示中出现），可以添加指导来引导它。与往常一样，在更改提示词时请衡量对性能的影响。例如：

```text
思考会增加延迟，仅当它能显著提升答案质量时才应使用——通常是需要多步推理的问题。如有疑问，直接回复即可。
```

相反，如果你在 `medium` effort 下运行困难的工作负载并出现了思考不足，首要手段是提高 effort 级别。如果需要更精细的控制，直接在提示词中说明。

<Note>
如果你在 `max` 或 `xhigh` effort 下运行 Claude Opus 4.7，请设置较大的 max output token 预算，以便模型有空间在其子智能体和工具调用中进行思考和行动。我们建议从 64k tokens 开始，然后根据情况进行调整。
</Note>

### 工具使用触发

Claude Opus 4.7 倾向于比 Claude Opus 4.6 更少使用工具，而更多地使用推理。这在大多数情况下会产生更好的结果。然而，提高 effort 设置是增加工具使用水平的有效手段，尤其是在知识工作中。`high` 或 `xhigh` effort 设置在智能体搜索和编码中显示出显著更多的工具使用。对于希望增加工具使用的场景，你也可以调整提示词，明确指示模型何时以及如何正确使用其工具。例如，如果发现模型没有使用你的网络搜索工具，请清晰地说明它应该使用的原因和方式。

### 面向用户的进度更新

Claude Opus 4.7 在长智能体执行过程中会提供更规律、更高质量的更新。如果你之前添加了强制中间状态信息的脚手架（例如“每 3 次工具调用后总结进度”），请尝试移除它。如果发现 Claude Opus 4.7 面向用户的更新的长度或内容对你的用例来说不够合适，请在提示词中明确描述这些更新应该是什么样子，并提供示例。

### 更字面化的指令遵循

Claude Opus 4.7 比 Claude Opus 4.6 更字面、更明确地解释提示词，尤其是在较低 effort 级别。它不会将一条指令从一个项目静默推广到另一个项目，也不会推断你没有提出的要求。这种字面化的好处是精确且减少波动，并且对于提示词精心调优的 API 用例、结构化提取以及需要可预测行为的流水线来说，通常表现更好。如果你需要 Claude 广泛地应用某条指令，请明确说明范围（例如，“将此格式应用于每个部分，而不仅仅是第一个”）。

### 语气与写作风格

与任何新模型一样，长篇写作的散文风格可能会发生变化。Claude Opus 4.7 更直接、更有主见，相比 Claude Opus 4.6 那种更温暖的风格，它更少使用验证性措辞和表情符号。如果你的产品依赖特定的语气，请根据新的基准重新评估风格提示词。

例如，如果你的产品语气更温暖或更具对话性，可以添加：

```text
使用温暖、协作的语气。在回答前先确认用户的表述。
```

### 控制子智能体生成

Claude Opus 4.7 默认倾向于生成更少的子智能体。然而，这种表现可以通过提示词进行引导；给 Claude Opus 4.7 明确的指导，说明何时使用子智能体是合适的。一个用于编码用例的简单示例：

```text
不要为你可以在单次回复中直接完成的工作生成子智能体（例如，重构一个你已经能看到的函数）。

当需要同时处理多个项目或读取多个文件时，在同一轮中生成多个子智能体。
```

### 设计与前端默认风格

Claude Opus 4.7 拥有比 Claude Opus 4.6 更强的设计直觉，并有一致的默认室内风格：温暖的奶油色/米白色背景（约 `#F4F1EA`）、衬线显示字体（Georgia、Fraunces、Playfair）、斜体字重音以及陶土色/琥珀色强调色。这种风格在编辑、酒店业和作品集类简报中读起来不错，但对于仪表板、开发工具、金融科技、医疗保健或企业级应用来说会显得不合适——而且它既出现在幻灯片中也出现在 Web UI 中。

这个默认风格是顽固的。通用的指令（“不要用奶油色”、“让它干净极简”）往往会让模型转向另一个固定的调色板，而不是产生多样性。有两种方法可靠有效：

**1. 指定具体的替代方案。** 模型会精确遵循明确的规格说明：

```text
为一个名为 AEFRM 的保健品品牌设计一个桌面着陆页。

视觉方向应源自冷峻的单色氛围，使用从浅银灰色逐渐过渡到蓝灰色和近黑色的色调，类似于雾面金属表面。

页面应感觉锐利且受控，具有强烈的结构感和克制感。

在整个页面中使用这种色调系统，不要引入明亮的强调色。

在英雄设计中使用上传的图像，并处理为黑白。

布局应通过清晰的水平区块和居中的最大宽度容器来构建。在卡片、按钮、输入框和媒体框架上一致使用 4px 圆角。边距应感觉宽松，每个区块周围留有足够的空白空间，使页面能够呼吸。

排版应使用方形、有棱角的无衬线字体，字母间距比通常更宽，尤其是在标题和导航中，使文本感觉更具工程感、更不紧凑。标题文字可以是大写的大号字体，而辅助文案保持简短稀疏。副文本应使用 Alumni Sans SC，大小为 4-6px，像底部中央角落那样的小小文字。

在结构上，从英雄区开始，包含一个有力的产品陈述、一个简短的支撑段落和一个干净的产品占位符或包装效果图。在其下方添加一个包含三到四个区块的优势网格，然后是一个配方或成分部分，最后是一个 CTA。

按钮应为扁平、精确的，带有细微的悬停变化，使用 transition: all 160ms ease-out，其中亮度和边框对比度略有变化，而不是使用剧烈的动态效果。

调色板应保持在此范围内：
#E9ECEC, #C9D2D4, #8C9A9E, #44545B, #11171B。
```

**2. 让模型在构建前先提出选项。** 这会打破默认风格，并让用户获得控制权。如果你以前依赖 `temperature` 来获得设计多样性，请使用此方法——它会在多次运行中产生有意义的不同方向。示例提示词：

```text
在构建之前，针对此简报提出 4 种不同的视觉方向（每种包含：背景十六进制色 / 强调色十六进制色 / 字体 — 一行理由）。请用户选择一个，然后仅实现该方向。
```

此外，Claude Opus 4.7 所需的前端设计提示词比以往模型更少，就能避免用户称之为“AI 生成内容审美”的通用模式。对于早期模型，我们在[前端设计技能](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md)中推荐了一个较长的提示词片段。然而，Claude Opus 4.7 只需要更少的提示词指导就能生成独特、有创意的前端。以下提示词片段与上述关于多样性的建议配合良好：

```text
<frontend_aesthetics>
永远不要使用通用的 AI 生成审美，例如过度使用的字体系列（Inter、Roboto、Arial、系统字体）、陈旧的配色方案（特别是白色或深色背景上的紫色渐变）、可预测的布局和组件模式，以及缺乏上下文特定特色的千篇一律的设计。使用独特的字体、一致的色彩和主题，以及用于效果和微交互的动画。
</frontend_aesthetics>
```

### 交互式编码产品

Claude Opus 4.7 的 token 使用和行为在自主的、异步的编码智能体（单次用户轮次）与交互式的、同步的编码智能体（多次用户轮次）之间可能不同。具体来说，它在交互式环境中倾向于使用更多 token，主要原因是它在用户轮次后会进行更多推理。这可以改善长时间的、交互式编码会话中的长周期连贯性、指令遵循和编码能力，但同时也带来更多的 token 使用。为了在编码产品中最大化性能和 token 效率，我们建议使用 `xhigh` 或 `high` effort，添加自主功能（如自动模式），并减少用户所需的交互次数。

当然，在限制所需用户交互次数时，在第一个人类轮次中预先说明任务、意图和相关约束是很重要的。提供明确、清晰、准确的任务描述，有助于在最小化用户轮次后额外 token 使用的同时，最大限度地提高自主性和智能性。我们发现，由于 Claude Opus 4.7 比之前的模型更具自主性，这种使用模式有助于最大化性能。相比之下，在多个用户轮次中逐步传达的模糊或不明确的提示词，往往会相对降低 token 效率，有时也会降低性能。

### 代码审查工具

Claude Opus 4.7 在发现 bug 方面比之前的模型有明显提升，在我们的评估中召回率和精确度都更高——在基于真实 Anthropic PR 的最难的 bug 发现评估中，召回率提高了 11 个百分点。然而，如果你的代码审查工具是为早期模型调优的，你最初可能会看到召回率下降。这很可能是工具效应，而不是能力倒退。当审查提示词包含诸如“仅报告高严重性问题”、“保守一些”或“不要吹毛求疵”之类的指令时，Claude Opus 4.7 可能比早期模型更忠实地遵循该指令——它可能会同样彻底地调查代码、识别 bug，然后不报告那些它判断为低于你设定标准的发现。这可能表现为模型进行了相同深度的调查，但将较少的调查转化为报告的发现，尤其是在较低严重性的 bug 上。精确度通常会上升，但测量的召回率可能下降，即使模型底层的 bug 发现能力已经提高。

一些推荐的提示词措辞：

```text
报告你发现的每一个问题，包括你不确定或认为低严重性的问题。在此阶段不要根据重要性或信心进行筛选——后续的独立验证步骤会做这件事。你的目标是覆盖率：提供一个后来被过滤掉的发现，也比默默漏掉一个真正的 bug 要好。对于每个发现，请包含你的信心级别和估计的严重性，以便下游过滤器可以对其进行排序。
```

即使没有实际的第二步，也可以使用此提示词，但将信心过滤移出发现步骤通常是有帮助的。如果你的工具有独立的验证、去重或排序阶段，请明确告诉模型其在发现阶段的工作是覆盖率，而不是筛选。

如果你确实希望模型在单次通过中自我筛选，请具体说明标准，而不是使用“重要”这样的定性术语——例如，“报告任何可能导致不正确行为、测试失败或误导性结果的 bug；只忽略纯粹的样式或命名偏好之类的细枝末节”。

我们建议针对你的评估或测试用例的子集迭代提示词，以验证召回率或 F1 分数的提升。

### 计算机使用

[计算机使用](/docs/en/agents-and-tools/tool-use/computer-use-tool)能力适用于多种分辨率，最高可达新的最大分辨率 2576px / 3.75MP。在我们的计算机使用测试中，我们发现以 1080p 发送图像在性能和成本之间提供了良好的平衡。

对于对成本特别敏感的工作负载，我们推荐 720p 或 1366×768 作为成本较低且性能强劲的选项。我们建议你自行测试，为你的用例找到理想的设置；尝试不同的 effort 设置也有助于调整模型的行为。

## 通用原则

### 清晰直接

Claude 对清晰、明确的指令反应良好。对期望输出进行具体描述有助于提升结果质量。如果你希望有“超越预期”的表现，请明确要求，而不是依赖模型从模糊的提示词中推断。

可以把 Claude 看作一位聪明但缺乏你所在团队规范和流程背景的新员工。你解释得越精确，结果就越好。

**黄金法则：** 将你的提示词展示给一位对任务背景了解不多的同事，请他们按照提示词执行。如果他们感到困惑，Claude 也会困惑。

- 具体说明期望的输出格式和约束条件。
- 当顺序或完整性很重要时，使用编号列表或项目符号将指令组织为连续的步骤。

<section title="示例：创建分析仪表板">

**效果较差的写法：**
```text
创建一个分析仪表板
```

**效果更好的写法：**
```text
创建一个分析仪表板。包含尽可能多的相关特性和交互。超越基础，创建一个功能齐全的实现。
```

</section>

### 添加上下文以提升性能

提供指令背后的背景或动机，例如向 Claude 解释为什么某种行为很重要，可以帮助 Claude 更好地理解你的目标并提供更有针对性的回复。

<section title="示例：格式偏好">

**效果较差的写法：**
```text
永远不要使用省略号
```

**效果更好的写法：**
```text
你的回复将由文本转语音引擎朗读，因此永远不要使用省略号，因为文本转语音引擎不知道如何发音。
```

</section>

Claude 足够聪明，能够从解释中进行泛化。

### 有效使用示例

示例是引导 Claude 输出格式、语气和结构的最可靠方法之一。几个精心设计的示例（称为 few-shot 或少样本提示）可以显著提高准确性和一致性。

添加示例时，确保它们：
- **相关：** 密切反映你的实际用例。
- **多样：** 覆盖边缘情况，并且变化足够多，以免 Claude 学到非预期的模式。
- **结构化：** 将示例包裹在 `<example>` 标签中（多个示例放在 `<examples>` 标签内），以便 Claude 能区分示例和指令。

<Tip>为获得最佳结果，建议包含 3-5 个示例。你也可以要求 Claude 评估你的示例的相关性和多样性，或者根据你初始的示例生成更多示例。</Tip>

### 使用 XML 标签结构化提示词

XML 标签有助于 Claude 无歧义地解析复杂的提示词，尤其是当提示词混合了指令、上下文、示例和变量输入时。将每种内容类型包裹在各自的标签中（例如 `<instructions>`、`<context>`、`<input>`）可以减少误解。

最佳实践：
- 在提示词中使用一致、描述性的标签名称。
- 当内容具有自然层次结构时，使用嵌套标签（例如文档放在 `<documents>` 内，每个文档放在 `<document index="n">` 内）。

### 给 Claude 赋予角色

在系统提示中设定角色，可以使 Claude 的行为和语气聚焦于你的用例。即使是一句话也会带来不同：

```python Python
import anthropic

client = anthropic.Anthropic()

message = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=1024,
    system="你是一个乐于助人的编码助手，专精于 Python。",
    messages=[
        {"role": "user", "content": "如何按键对字典列表进行排序？"}
    ],
)
print(message.content)
```

### 长上下文提示词

当处理大型文档或数据密集型输入（20k+ tokens）时，请仔细构建提示词以获得最佳结果：

- **将长格式数据放在顶部**：将你的长文档和输入放在提示词顶部，位于查询、指令和示例之上。这可以显著提升所有模型的性能。

    </section>

- **基于引文进行回复**：对于长文档任务，要求 Claude 在执行任务之前先从文档中引用相关部分。这有助于 Claude 从文档其他内容的噪音中筛选出关键信息。

## 输出与格式化

### 沟通风格与冗长度

与之前的模型相比，Claude 的最新模型具有更简洁、更自然的沟通风格：

- **更直接、更扎实：** 提供基于事实的进度报告，而不是自我夸耀的更新
- **更具对话性：** 更流畅、更口语化，少了一些机器感
- **更少冗余：** 为了提高效率，可能会跳过详细的总结，除非另有提示

这意味着 Claude 可能会在工具调用后省略口头总结，直接跳转到下一个操作。如果你希望更清晰地了解其推理过程：

```text 提示示例
在完成涉及工具使用的任务后，快速总结一下你已完成的工作。
```

### 控制回复格式

有几种特别有效的方法可以引导输出格式：

1. **告诉 Claude 要做什么，而不是不要做什么**

   - 避免使用：“不要在回复中使用 markdown”
   - 尝试使用：“你的回复应由流畅的散文段落组成。”

2. **使用 XML 格式指示符**

   - 尝试使用：“将回复中的散文部分放在 \<smoothly_flowing_prose_paragraphs\> 标签中。”

3. **使提示词风格与期望输出相匹配**

   提示词中使用的格式风格可能会影响 Claude 的回复风格。如果你在输出格式的可控性方面仍然遇到问题，请尝试使你的提示词风格尽可能接近期望的输出风格。例如，从提示词中移除 markdown 可以减少输出中的 markdown 数量。

4. **使用详细的提示词来表达特定的格式偏好**

   为了对 markdown 和格式的使用进行更精细的控制，请提供明确的指导：

```text 最小化 markdown 的提示示例
<avoid_excessive_markdown_and_bullet_points>
在撰写报告、文档、技术说明、分析或任何长篇内容时，使用清晰、流畅的散文，采用完整的段落和句子。使用标准的段落分隔符进行组织，并保留 markdown 主要用于 `内联代码`、代码块 (```...```) 和简单的标题 (###, ###)。避免使用 **粗体** 和 *斜体*。

除非：a) 你在展示真正离散的项目，列表格式是最佳选择，或 b) 用户明确要求列表或排名，否则不要使用有序列表 (1. ...) 或无序列表 (*)。

不要用项目符号或数字列出项目，而是将它们自然地融入句子中。此指导尤其适用于技术写作。使用散文而不是过多的格式将提高用户满意度。永远不要输出一系列过短的要点。

你的目标是可读、流畅的文本，自然地引导读者理解思想，而不是将信息碎片化为孤立的要点。
</avoid_excessive_markdown_and_bullet_points>
```

### LaTeX 输出

Claude Opus 4.6 默认使用 LaTeX 表示数学表达式、方程和技术说明。如果你更喜欢纯文本，请在提示词中添加以下指令：

```text 提示示例
仅使用纯文本格式回复。不要使用 LaTeX、MathJax 或任何标记符号，如 \( \)、$ 或 \frac{}{}。使用标准文本字符编写所有数学表达式（例如，用 "/" 表示除法，"*" 表示乘法，"^" 表示指数）。
```

### 文档创建

Claude 的最新模型在创建演示文稿、动画和视觉文档方面表现出色，具有令人印象深刻的创造力和强大的指令遵循能力。在大多数情况下，这些模型能在第一次尝试时就生成精致、可用的输出。

文档创建的最佳实践：

```text 提示示例
创建一个关于 [主题] 的专业演示文稿。在适当的地方加入深思熟虑的设计元素、视觉层次和引人入胜的动画。
```

### 迁移离开预填充回复

从 Claude 4.6 模型和 [Claude Mythos Preview](https://anthropic.com/glasswing) 开始，不再支持在最后一轮助手回复中进行预填充。在 Mythos Preview 上，包含预填充助手消息的请求会返回 400 错误。模型智能和指令遵循能力已经进步，大多数预填充的用例不再需要它。现有模型将继续支持预填充，而在对话其他位置添加助手消息则不受影响。

以下是一些常见的预填充场景以及如何迁移：

<section title="控制输出格式">

预填充曾被用来强制特定的输出格式，如 JSON/YAML、分类等，预填充可以将 Claude 约束到特定的结构。

**迁移：** [结构化输出](/docs/en/build-with-claude/structured-outputs) 功能专门设计用于约束 Claude 的回复以遵循给定的 schema。可以先尝试直接要求模型符合你的输出结构，因为较新的模型在被要求时能够可靠地匹配复杂的 schema，尤其是结合重试机制。对于分类任务，可以使用带有包含有效标签的 enum 字段的工具，或使用结构化输出。

</section>

<section title="消除开场白">

预填充如“这是所要求的摘要：\n”曾被用来跳过介绍性文字。

**迁移：** 在系统提示中使用直接指令：“直接回复，不要开场白。不要以‘这是...’、‘基于...’等短语开头。” 或者，引导模型在 XML 标签内输出，使用结构化输出，或使用工具调用。如果偶尔有开场白出现，可以在后处理中将其剥离。

</section>

<section title="避免不当拒绝">

预填充曾被用来引导模型绕过不必要的拒绝。

**迁移：** Claude 现在在不恰当拒绝方面表现好得多。在 `user` 消息中进行清晰的提示（无需预填充）应该就足够了。

</section>

<section title="续写">

预填充曾被用来继续部分补全、恢复中断的回复，或从上一个生成停止的地方继续。

**迁移：** 将续写内容移到用户消息中，并包含中断回复的最后文本：“你之前的回复被中断，并以 `[previous_response]` 结尾。请从你停止的地方继续。” 如果这是错误处理或不完整回复处理的一部分，并且没有用户体验成本，可以重试请求。

</section>

<section title="上下文注入与角色一致性">

预填充曾被用来定期确保刷新或注入上下文。

**迁移：** 对于非常长的对话，将之前预填充的助手提醒注入到用户轮次中。如果上下文注入是更复杂的智能体系统的一部分，可以考虑通过工具进行注入（例如，基于启发式规则（如轮次数量）暴露或鼓励使用包含上下文的工具），或在上下文压缩时进行。

</section>

## 工具使用

### 工具使用行为

Claude 的最新模型经过精确指令遵循的训练，并从明确的指导中获益，以使用特定的工具。如果你说“你能建议一些更改吗”，Claude 有时会提供建议而不是直接实施，即使实施更改可能才是你的本意。

为了让 Claude 采取行动，请更明确：

<section title="示例：明确的指令">

**效果较差（Claude 只会建议）：**
```text
你能建议一些更改来改进这个函数吗？
```

**效果更好（Claude 会进行更改）：**
```text
更改此函数以提高其性能。
```

或：
```text
对身份验证流程进行这些编辑。
```

</section>

为了让 Claude 默认更主动地采取行动，你可以在系统提示中添加：

```text 主动行动的提示示例
<default_to_action>
默认情况下，实施更改而不仅仅是建议它们。如果用户的意图不明确，推断最可能有用的操作并继续执行，使用工具发现任何缺失的细节而不是猜测。尝试推断用户是否意图进行工具调用（例如，文件编辑或读取），并据此采取行动。
</default_to_action>
```

另一方面，如果你希望模型默认更谨慎，不那么急于直接实施，并且只在被要求时才采取行动，可以用如下提示词引导此行为：

```text 保守行动的提示示例
<do_not_act_before_instructions>
除非明确指示进行更改，否则不要急于实施或更改文件。当用户的意图不明确时，默认提供信息、进行研究和提供建议，而不是采取行动。仅在用户明确要求时才进行编辑、修改或实施。
</do_not_act_before_instructions>
```

Claude Opus 4.5 和 Claude Opus 4.6 也比以前的模型对系统提示更敏感。如果你的提示词是为了减少工具或技能触发不足而设计的，这些模型现在可能会触发过度。解决方法是将任何激进的措辞调回。在你之前可能会说“关键：你必须使用此工具当...”的地方，现在可以使用更正常的提示，如“当...时使用此工具”。

### 优化并行工具调用

Claude 的最新模型擅长并行执行工具。这些模型会：

- 在研究期间运行多个推测性搜索
- 同时读取多个文件以更快地构建上下文
- 并行执行 bash 命令（这甚至可能成为系统性能的瓶颈）

这种行为很容易引导。虽然模型在没有特别提示的情况下并行工具调用的成功率已经很高，但你可以将其提升到接近 100% 或调整其激进程度：

```text 最大化并行效率的提示示例
<use_parallel_tool_calls>
如果你打算调用多个工具，且这些工具调用之间没有依赖关系，请并行发起所有独立的工具调用。优先考虑同时调用工具，而不是顺序执行。例如，在读取 3 个文件时，并行运行 3 个工具调用，同时将所有 3 个文件读入上下文。尽可能最大化并行工具调用以提高速度和效率。但是，如果某些工具调用依赖于先前的调用来提供参数等依赖值，请不要并行调用这些工具，而应按顺序调用。永远不要在工具调用中使用占位符或猜测缺失的参数。
</use_parallel_tool_calls>
```

```text 减少并行执行的提示示例
顺序执行操作，每个步骤之间短暂暂停以确保稳定性。
```

## 思考与推理

### 过度思考与过分详尽

Claude Opus 4.6 比之前的模型进行了更多的预先探索，尤其是在更高的 `effort` 设置下。这种初始工作通常有助于优化最终结果，但模型可能会在未被提示的情况下收集广泛的上下文或进行多线索研究。如果你的提示词以前鼓励模型更加详尽，你应该针对 Claude Opus 4.6 调整该指导：

- **用更有针对性的指令替换笼统的默认设置。** 不要使用“默认使用 [工具]”，而应添加指导，如“当 [工具] 能增强你对问题的理解时再使用它。”
- **移除过度提示。** 在之前模型中触发不足的工具现在很可能会适当触发。像“如有疑问，请使用 [工具]”这样的指令会导致过度触发。
- **使用 effort 作为回退。** 如果 Claude 仍然过于激进，可以使用较低的 `effort` 设置。

在某些情况下，Claude Opus 4.6 可能会进行大量思考，这会膨胀思考 token 并减慢响应速度。如果这种行为是不可取的，你可以添加明确的指令来约束其推理，或者降低 `effort` 设置以减少整体思考和 token 使用。

```text 提示示例
当你决定如何处理一个问题时，选择一个方法并坚持执行。避免重新审视决策，除非你遇到了直接反驳你推理的新信息。如果你在权衡两种方法，选择一种并坚持下去。如果所选方法失败，你可以在以后纠正方向。
```

如果你需要对思考成本设置硬性上限，Opus 4.6 和 Sonnet 4.6 上带有 `budget_tokens` 上限的扩展思考仍然有效，但已被弃用。建议降低 [effort](/docs/en/build-with-claude/effort) 设置，或使用 `max_tokens` 作为硬性限制配合[自适应思考](/docs/en/build-with-claude/adaptive-thinking)。

### 利用思考与交错思考能力

Claude 的最新模型提供了思考能力，这对于工具使用后的反思或复杂的多步推理任务尤其有帮助。你可以引导其初始或交错的思考以获得更好的结果。

Claude Opus 4.6 和 Claude Sonnet 4.6 使用[自适应思考](/docs/en/build-with-claude/adaptive-thinking)（`thinking: {type: "adaptive"}`），Claude 会动态决定何时思考以及思考多少。Claude 根据两个因素校准思考：`effort` 参数和查询复杂度。更高的 effort 会引发更多思考，更复杂的查询也是如此。对于不需要思考的简单查询，模型会直接回复。在内部评估中，自适应思考始终比扩展思考带来更好的性能。考虑转向自适应思考以获得最智能的回复。

将自适应思考用于需要智能体行为的工作负载，例如多步工具使用、复杂的编码任务和长周期智能体循环。较旧的模型使用带有 `budget_tokens` 的手动思考模式。

你可以引导 Claude 的思考行为：

```text 提示示例
收到工具结果后，仔细反思其质量，并确定最佳后续步骤，然后再继续。使用你的思考来根据这些新信息进行规划和迭代，然后采取最佳的下一个行动。
```

自适应思考的触发行为是可提示的。如果发现模型思考的频率过高（这可能在大型或复杂的系统提示中出现），请添加指导来引导它：

```text 提示示例
扩展思考会增加延迟，仅当它能显著提升答案质量时才应使用——通常是需要多步推理的问题。如有疑问，直接回复即可。
```

如果你正在从带有 `budget_tokens` 的[扩展思考](/docs/en/build-with-claude/extended-thinking)迁移，请替换你的思考配置，并将预算控制移至 `effort`：

**之前（扩展思考，旧模型）：**

```python Python nocheck
client.messages.create(
    model="claude-sonnet-4-5-20250929",
    max_tokens=64000,
    thinking={"type": "enabled", "budget_tokens": 32000},
    messages=[{"role": "user", "content": "..."}],
)
```

**之后（自适应思考）：**

```python Python nocheck
client.messages.create(
    model="claude-opus-4-7",
    max_tokens=64000,
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},  # 或 "max", "xhigh", "medium", "low"
    messages=[{"role": "user", "content": "..."}],
)
```

如果你没有使用扩展思考，则无需更改。当你省略 `thinking` 参数时，思考默认是关闭的。

- **优先使用通用指令而非预设步骤。** 像“彻底思考”这样的提示通常比手工编写的逐步计划产生更好的推理。Claude 的推理能力常常超出人类的预设。
- **多示例（Multishot）与思考配合使用。** 在 few-shot 示例中使用 `<thinking>` 标签向 Claude 展示推理模式。它会将该风格泛化到自己的扩展思考块中。
- **手动 CoT 作为回退。** 当思考关闭时，你仍然可以通过要求 Claude 逐步思考问题来鼓励逐步推理。使用 `<thinking>` 和 `<answer>` 等结构化标签将推理与最终输出清晰分离。
- **要求 Claude 自我检查。** 添加类似“在完成之前，请根据 [测试标准] 验证你的答案”的内容。这能可靠地捕获错误，尤其适用于编码和数学。

<Note>当扩展思考被禁用时，Claude Opus 4.5 对“think”及其变体词特别敏感。在这种情况下，考虑使用“consider”、“evaluate”或“reason through”等替代词。</Note>

<Info>
  有关思考能力的更多信息，请参阅[扩展思考](/docs/en/build-with-claude/extended-thinking)和[自适应思考](/docs/en/build-with-claude/adaptive-thinking)。
</Info>

## 智能体系统

### 长周期推理与状态跟踪

Claude 的最新模型擅长长周期推理任务，具有卓越的状态跟踪能力。Claude 通过专注于增量进展（每次只稳步推进几件事，而不是试图一次完成所有事情）来在长时间会话中保持方向感。这种能力在多个上下文窗口或任务迭代中尤其明显，Claude 可以处理复杂任务、保存状态，并使用全新的上下文窗口继续工作。

#### 上下文感知与多窗口工作流

Claude 4.6 和 Claude 4.5 模型具备[上下文感知](/docs/en/build-with-claude/context-windows#context-awareness-in-claude-sonnet-4-6-sonnet-4-5-and-haiku-4-5)能力，使模型能够在整个对话过程中跟踪其剩余的上下文窗口（即“token 预算”）。这使得 Claude 能够通过了解自己有多少可用空间，更有效地执行任务和管理上下文。

**管理上下文限制：**

如果你在智能体脚手架中使用 Claude，该脚手架会压缩上下文或允许将上下文保存到外部文件（如 Claude Code 中），请考虑将此信息添加到提示词中，以便 Claude 相应地调整行为。否则，Claude 有时可能会在接近上下文限制时自然地尝试收尾工作。以下是一个示例提示词：

```text 提示示例
你的上下文窗口在接近其限制时会自动压缩，使你能够从离开的地方无限期地继续工作。因此，不要因为 token 预算的担忧而过早停止任务。当接近 token 预算限制时，在上下文窗口刷新之前将当前的进度和状态保存到记忆中。始终保持尽可能的持久和自主，即使预算即将用完也要完全完成任务。无论剩余上下文多少，永远不要人为地提前停止任何任务。
```

[记忆工具](/docs/en/agents-and-tools/tool-use/memory-tool)与上下文感知自然结合，可实现无缝的上下文转换。

#### 多上下文窗口工作流

对于跨越多个上下文窗口的任务：

1. **对第一个上下文窗口使用不同的提示词**：使用第一个上下文窗口来设置框架（编写测试、创建设置脚本），然后使用后续的上下文窗口在待办列表上进行迭代。
2. **让模型以结构化格式编写测试**：要求 Claude 在开始工作之前创建测试，并以结构化格式（例如 `tests.json`）跟踪它们。这能带来更好的长期迭代能力。提醒 Claude 测试的重要性：“删除或编辑测试是不可接受的，因为这可能导致功能缺失或出现 bug。”
3. **设置提升生活质量的工具**：鼓励 Claude 创建设置脚本（例如 `init.sh`）以优雅地启动服务器、运行测试套件和 linter。这可以防止在从全新上下文窗口继续时重复工作。
4. **全新开始 vs 压缩**：当上下文窗口被清除时，考虑使用全新的上下文窗口而不是使用压缩。Claude 的最新模型在从本地文件系统发现状态方面极其有效。在某些情况下，你可能希望利用这一点而不是压缩。具体说明它应该如何开始：
   - “调用 pwd；你只能在此目录中读取和写入文件。”
   - “查看 progress.txt、tests.json 和 git 日志。”
   - “在继续实现新功能之前，手动运行基本集成测试。”
5. **提供验证工具**：随着自主任务长度的增加，Claude 需要在不依赖持续人工反馈的情况下验证正确性。像 Playwright MCP 服务器或用于测试 UI 的计算机使用能力这样的工具会很有帮助。
6. **鼓励充分利用上下文**：提示 Claude 在继续之前高效地完成组件：

```text 提示示例
这是一个非常长的任务，因此清晰地规划你的工作可能是有益的。鼓励你花费整个输出上下文来处理任务——只需确保不要在未提交重要工作的情况下耗尽上下文。继续系统性地工作，直到完成此任务。
```

#### 状态管理最佳实践

- **对状态数据使用结构化格式**：当跟踪结构化信息（如测试结果或任务状态）时，使用 JSON 或其他结构化格式帮助 Claude 理解 schema 要求。
- **对进度说明使用非结构化文本**：自由形式的进度说明对于跟踪总体进度和上下文效果很好。
- **使用 git 进行状态跟踪**：Git 提供了已完成工作的日志和可以恢复的检查点。Claude 的最新模型在使用 git 跨多个会话跟踪状态方面表现尤为出色。
- **强调增量进展**：明确要求 Claude 跟踪其进度并专注于增量工作。

### 平衡自主性与安全性

如果没有指导，Claude Opus 4.6 可能会采取难以撤销或影响共享系统的操作，例如删除文件、强制推送或发布到外部服务。如果你希望 Claude Opus 4.6 在采取潜在风险操作之前进行确认，请在提示词中添加指导：

```text 提示示例
考虑操作的可逆性和潜在影响。鼓励你采取本地的、可逆的操作，如编辑文件或运行测试，但对于难以撤销、影响共享系统或可能具有破坏性的操作，在继续之前请询问用户。

需要确认的操作示例：
- 破坏性操作：删除文件或分支、删除数据库表、rm -rf
- 难以撤销的操作：git push --force、git reset --hard、修改已发布的提交
- 对其他用户可见的操作：推送代码、评论 PR/议题、发送消息、修改共享基础设施

遇到障碍时，不要使用破坏性操作作为捷径。例如，不要绕过安全检查（如 --no-verify）或丢弃可能包含进行中工作的不熟悉文件。
```

### 研究与信息收集

Claude 的最新模型展示了卓越的智能体搜索能力，能够有效地从多个来源查找和综合信息。为了获得最佳研究结果：

1. **提供明确的成功标准**：定义什么构成对你研究问题的成功答案。
2. **鼓励来源验证**：要求 Claude 在多个来源之间验证信息。
3. **对于复杂的研究任务，使用结构化方法**：

```text 复杂研究提示示例
以结构化的方式搜索此信息。在收集数据时，发展几个相互竞争的假设。在进度说明中跟踪你的置信水平以改善校准。定期自我批评你的方法和计划。更新假设树或研究笔记文件以持久化信息并提供透明度。系统地分解这个复杂的研究任务。
```

这种结构化的方法使 Claude 能够查找和综合几乎任何信息，并迭代地批评其发现，无论语料库有多大。

### 子智能体编排

Claude 的最新模型显示出显著改进的原生子智能体编排能力。这些模型能够识别出何时将工作委派给专门的子智能体是有益的，并在不需要明确指令的情况下主动这样做。

为了利用这种行为：

1. **确保定义良好的子智能体工具**：拥有可用的子智能体工具并在工具定义中进行描述。
2. **让 Claude 自然编排**：Claude 会在不需要明确指令的情况下适当地进行委派。
3. **注意过度使用**：Claude Opus 4.6 对子智能体有强烈的偏好，可能会在更简单、直接的方法就足够的情况下生成子智能体。例如，模型可能会为代码探索生成子智能体，而直接使用 grep 调用更快且足够。

如果你看到过度使用子智能体，请添加明确的指导，说明何时应该以及何时不应该使用子智能体：

```text 子智能体使用提示示例
当任务可以并行运行、需要隔离上下文或涉及不需要共享状态的独立工作流时，使用子智能体。对于简单任务、顺序操作、单文件编辑或需要在步骤之间保持上下文的任务，请直接工作，而不是委派。
```

### 链接复杂提示词

借助自适应思考和子智能体编排，Claude 在内部处理大多数多步推理。当需要检查中间输出或强制特定的流水线结构时，显式的提示词链接（将任务分解为顺序的 API 调用）仍然很有用。

最常见的链接模式是**自我修正**：生成草稿 → 让 Claude 根据标准审查 → 让 Claude 根据审查进行改进。每一步都是一个单独的 API 调用，因此你可以在任何点记录、评估或分支。

### 减少智能体编码中的文件创建

Claude 的最新模型有时可能会为测试和迭代目的创建新文件，尤其是在处理代码时。这种方法允许 Claude 使用文件（尤其是 Python 脚本）作为“临时草稿纸”，然后再保存最终输出。使用临时文件可以改善结果，特别是对于智能体编码用例。

如果你希望尽量减少新文件的创建，可以指示 Claude 自行清理：

```text 提示示例
如果你创建了任何临时的、用于迭代的新文件、脚本或辅助文件，请在任务结束时清理并删除它们。
```

### 过度热情

Claude Opus 4.5 和 Claude Opus 4.6 倾向于过度设计，例如创建额外文件、添加不必要的抽象，或构建未被要求的灵活性。如果你看到这种不良行为，请添加具体指导以保持解决方案的最小化。

例如：

```text 最小化过度设计的提示示例
避免过度设计。只进行直接要求或明确必要的更改。保持解决方案简单且专注：

- 范围：不要添加功能、重构代码或进行超出要求的“改进”。一个 bug 修复不需要清理周围的代码。一个简单的功能不需要额外的可配置性。

- 文档：不要为你未更改的代码添加文档字符串、注释或类型注解。仅在逻辑不不言自明的地方添加注释。

- 防御性编程：不要为不可能发生的场景添加错误处理、回退或验证。信任内部代码和框架的保证。仅在系统边界（用户输入、外部 API）进行验证。

- 抽象：不要为一次性操作创建辅助函数、工具或抽象。不要为假设的未来需求设计。正确的复杂度是当前任务所需的最小值。
```

### 避免专注于通过测试和硬编码

Claude 有时可能过于专注于让测试通过，而牺牲了更通用的解决方案，或者可能使用变通方法（如辅助脚本）进行复杂的重构，而不是直接使用标准工具。为了防止这种行为并确保健壮、通用的解决方案：

```text 提示示例
请使用可用的标准工具编写高质量、通用的解决方案。不要创建辅助脚本或变通方法以更高效地完成任务。实现一个对所有有效输入都正确工作的解决方案，而不仅仅是对测试用例。不要硬编码值或创建仅对特定测试输入有效的解决方案。相反，实现能普遍解决问题的实际逻辑。

专注于理解问题需求并实现正确的算法。测试用于验证正确性，而不是定义解决方案。提供一个遵循最佳实践和软件设计原则的原则性实现。

如果任务不合理或不可行，或者任何测试不正确，请告知我，而不是绕过它们。解决方案应该是健壮、可维护和可扩展的。
```

### 最小化智能体编码中的幻觉

Claude 的最新模型更不容易产生幻觉，并能基于代码给出更准确、扎实、智能的答案。为了进一步鼓励这种行为并最小化幻觉：

```text 提示示例
<investigate_before_answering>
永远不要对你未打开的代码进行猜测。如果用户引用了特定文件，你必须在回答之前读取该文件。确保在回答关于代码库的问题之前进行调查并阅读相关文件。除非你确定正确答案，否则绝不要对代码做出任何断言——给出扎实、无幻觉的答案。
</investigate_before_answering>
```

## 迁移考虑

从早期版本迁移到 Claude 4.6 模型时：

1. **明确期望的行为**：考虑准确描述你希望在输出中看到的内容。
2. **使用修饰语来构建指令**：添加鼓励 Claude 提高输出质量和细节的修饰语，有助于更好地塑造 Claude 的表现。例如，与其使用“创建一个分析仪表板”，不如使用“创建一个分析仪表板。包含尽可能多的相关特性和交互。超越基础，创建一个功能齐全的实现。”
3. **明确要求特定功能**：动画和交互元素应在需要时明确要求。
4. **更新思考配置**：Claude 4.6 模型使用[自适应思考](/docs/en/build-with-claude/adaptive-thinking)（`thinking: {type: "adaptive"}`），而不是带有 `budget_tokens` 的手动思考。使用 [effort 参数](/docs/en/build-with-claude/effort)来控制思考深度。
5. **迁移离开预填充回复**：从 Claude 4.6 模型开始，最后一轮助手回复中的预填充已弃用。有关替代方案的详细指导，请参阅[迁移离开预填充回复](#migrating-away-from-prefilled-responses)。
6. **调整反懒惰提示**：如果你的提示词以前鼓励模型更详尽或更积极地使用工具，请减少该指导。Claude 4.6 模型明显更主动，可能会对先前模型所需的指令过度触发。

有关详细的迁移步骤，请参阅[迁移指南](/docs/en/about-claude/models/migration-guide)。

### 从 Claude Sonnet 4.5 迁移到 Claude Sonnet 4.6

Claude Sonnet 4.6 默认的 effort 级别为 `high`，而 Claude Sonnet 4.5 没有 effort 参数。在从 Claude Sonnet 4.5 迁移到 Claude Sonnet 4.6 时，请考虑调整 effort 参数。如果没有显式设置，你可能会因默认的 effort 级别而遇到更高的延迟。

**推荐的 effort 设置：**
- **`medium`**：适用于大多数应用程序
- **`low`**：适用于高容量或延迟敏感的工作负载
- 在 `medium` 或 `high` effort 下设置较大的 max output token 预算（建议 64k tokens），为模型的思考和行动留出空间

**何时改用 Opus 4.7：** 对于最困难、最长周期的问题（大规模代码迁移、深度研究、长时间自主工作），Opus 4.7 仍然是正确的选择。Sonnet 4.6 针对快速周转和成本效率最为重要的工作负载进行了优化。

#### 如果你没有使用扩展思考

如果你在 Claude Sonnet 4.5 上没有使用扩展思考，那么在 Claude Sonnet 4.6 上你可以继续不使用。你应该根据你的用例显式设置适当的 effort 级别。在禁用思考且使用 `low` effort 的情况下，你可以期望获得与 Claude Sonnet 4.5（无扩展思考）相似或更好的性能。

```python Python
client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=8192,
    thinking={"type": "disabled"},
    output_config={"effort": "low"},
    messages=[{"role": "user", "content": "..."}],
)
```

#### 如果你正在使用扩展思考

如果你在 Claude Sonnet 4.5 上使用了带有 `budget_tokens` 的扩展思考，它在 Claude Sonnet 4.6 上仍然有效，但已被弃用。请迁移到[自适应思考](/docs/en/build-with-claude/adaptive-thinking)和 [effort 参数](/docs/en/build-with-claude/effort)。

##### 迁移到自适应思考

自适应思考特别适合以下工作负载模式：

- **自主多步智能体：** 将需求转化为工作软件的编码智能体、数据分析流水线以及模型独立运行多步的 bug 发现。自适应思考让模型能够根据每一步校准其推理，在更长的轨迹中保持方向。对于这些工作负载，从 `high` effort 开始。如果延迟或 token 使用是问题，则降至 `medium`。
- **计算机使用智能体：** Claude Sonnet 4.6 使用自适应模式在计算机使用评估中达到了同类最佳的准确率。
- **双峰工作负载：** 混合简单和困难任务，其中自适应思考在简单查询上跳过思考，在复杂查询上进行深度推理。

使用自适应思考时，在你的任务上评估 `medium` 和 `high` effort。正确的级别取决于你的工作负载在质量、延迟和 token 使用之间的权衡。

```python Python nocheck
client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=64000,
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},
    messages=[{"role": "user", "content": "..."}],
)
```

##### 在迁移期间保留 budget_tokens

如果你在迁移期间需要临时保留 `budget_tokens`，大约 16k tokens 的预算为难题提供了空间，而没有 token 使用失控的风险。此配置已弃用，将在未来的模型版本中移除。

**对于编码用例**（智能体编码、工具密集型工作流、代码生成），从 `medium` effort 开始：

```python Python nocheck
client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=16384,
    thinking={"type": "enabled", "budget_tokens": 16384},
    output_config={"effort": "medium"},
    messages=[{"role": "user", "content": "..."}],
)
```

**对于聊天和非编码用例**（聊天、内容生成、搜索、分类），从 `low` effort 开始：

```python Python nocheck
client.messages.create(
```
